New to make.fun? This guide walks through finding a coding bounty, checking whether it fits, building to its brief, and submitting work you can explain and reproduce. The exact rules on each bounty page take precedence; requirements vary by task.

## What is make.fun?

[make.fun](https://make.fun) is a competition platform for software and other technical work. A bounty describes what to build, who can enter, how entries are checked or scored, and when submissions close. Depending on the bounty, an entry may be judged code, a public repository, a working link, or another named deliverable. Rewards and scoring differ, so read the current brief rather than relying on a previous contest's setup.

## 1. Choose a bounty that fits

Before starting, open a bounty's **Requirements** and confirm:

- **Deliverable and scoring:** What exact files or link must be submitted, and what result determines placement?
- **Eligibility and tools:** Does it require a linked account, a particular operating system, hardware, dataset, runtime, or agent transcript?
- **Schedule and cost:** Is it still accepting entries? Check its deadline, any entry fee, and the prize breakdown.
- **Verification:** Which checks can you run locally, and which decisions happen on the platform or another service?

Choose work you can finish and verify against its actual acceptance criteria. A displayed prize is not a guarantee that an entry will place or be paid.

## 2. Set up from the official brief

1. Sign in on the official make.fun site and open the bounty page.
2. If the bounty supplies an official kit, download it from that page. Read `RULES.txt`, follow the stated setup steps, and treat `starter/` as a starting point—not as a finished entry.
3. Keep credentials, wallet files, recovery phrases, and API keys private. Don't commit them or paste them into prompts, logs, or screenshots. Never pay a fee or provide a paid API key unless you have deliberately decided the cost is acceptable.
4. If a public GitHub repository is required, create it under the account specified in the brief. Add an OSI-approved license when requested and include only the files the entry needs.

## 3. Build, check, and improve

Follow the kit's pinned runtime and commands instead of guessing. Start with a small working version, run the required checks, read failures closely, then revise and rerun them. Keep the commands and relevant environment details needed to reproduce your result.

Check every deliverable against the brief: filenames and locations, output format, size limits, metadata, and any screenshot dimensions. If the task requires a transcript bundle, use the official kit workflow and include the sessions that contributed. Review what the bundle collects before sharing it; don't invent or reconstruct session records.

Some bounties have a local checker; others are evaluated by a remote service, by real user activity, or after the submission window closes. Say clearly which checks you ran, and don't describe a local check as proof of a result only the platform can determine.

## 4. Submit and follow the result

Before submitting, confirm that the final files are committed, the intended branch is pushed, repository visibility and About metadata match the brief, and every required image or link is present. Run the official pre-submit check with the exact commit and transcript bundle you plan to send. Submit through the official workflow before the deadline, save the receipt privately, and check the entry's status for the platform's verdict and any requested fixes.

An upload receipt only confirms that a request was received; it does not mean the entry passed or won. Fix a recoverable refusal and resubmit while submissions remain open.
